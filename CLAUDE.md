# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Red Regenerator ("Red.Regen") is a Microsoft Dynamics 365 Business Central (AL language) per-tenant extension. It adds a "contract" document type on top of Sales and Purchase Orders/Invoices so that recurring items (licenses, extended warranties, rentals, etc.) can be billed on a schedule: create a contract, accept/activate it, then regenerate (or renew) it periodically to spawn new sales/purchase documents.

The repo contains two independent AL apps, each a separate VS Code AL workspace folder with its own `app.json`:

- **`Red Regenerator/`** — the main app (id range 70600–70799, object namespace `Red.Regenerator`).
- **`Red Regenerator Test/`** — a dependent test app (id range 70800–70849, namespace `Red.Regenerator.Test`) containing AL test codeunits. It depends on the main app via `app.json`.

Open `Red.Regen.code-workspace` in VS Code to get both AL projects plus `Documentation/` as workspace folders — this is how the project is normally developed (AL Language extension for VS Code, not a general text editor project).

## Build, package, test

There is no npm/dotnet CLI build in this repo — everything goes through the **AL Language** VS Code extension or its MCP server tool equivalents (`al_compile`, `al_build`, `al_publish`, `al_run_tests`, see `Documentation/al-mcp-repo-setup.md`). If the `al-language` MCP server is configured and enabled, prefer those tools over asking the user to click around VS Code.

- **Compile / build**: AL: Package (or `al_build` and `al_compile` MCP tools). Built `.app` files land in `Red Regenerator/_Build` and `Red Regenerator/_Build - Archive` (not checked in beyond what's already committed as history — this project keeps built `.app` packages in the repo per version bump).
- **Bump version / build via skill**: use the `red-build-al` skill when asked to build/package/bump version — it bumps `app.json`'s version (major segment tracks the BC platform version) and writes the `.app` to `_builds` rather than the repo root.
- **Release**: use the `red-release-al` skill for a full release — it always runs docs update → translation sync → build, in that order. Don't skip steps or reorder them manually.
- **Run tests**: AL test codeunits live in `Red Regenerator Test/Test/*.Codeunit.al` (`TestSetup`, `RegeneratorTest`, `GeneratorTest`). Run via `al_run_tests` or VS Code's AL Test Tool against a published sandbox/container; there is no headless CLI test runner in this repo.
- **Symbol download**: run "AL: Download Symbols" in VS Code (or ensure `.alpackages` is populated) before expecting diagnostics/symbol search to work — the AL MCP server needs a populated `.alpackages` per project.
- **AL validation (AppSource compliance)**: `Scripts/RunALValidation.ps1` runs `Run-AlValidation` (BcContainerHelper) against built `.app` files for the configured affixes/countries. Requires a local BC14 install and a license file — largely a one-off/manual tool, most of the script is commented-out reference material.
- **Code signing**: `Scripts/Codesign.ps1` signs the apps under `_Build` with SignTool using the "Red and Bundle" cert (Sectigo/SafeNet token) — manual, admin PowerShell only.
- **Translations**: `Scripts/Translate.ps1` round-trips `.xlf` files through Excel via the ForNAV cmdlet DLL (export `.g.xlf` → Excel, import Excel → `.xlf`). Use the `fornav-translate` skill for translation work instead of running this by hand. Translation files live in `Red Regenerator/Translations/` (`da-DK`, `de-DE`, `en-US`, `es-MX`, `nl-NL`).
- **Code analysis**: CodeCop and PerTenantExtensionCop are enabled (`Red.Regen.code-workspace` → `al.codeAnalyzers`), ruleset at `.Rulesets/BC.ruleset.json`. That ruleset suppresses several rules (AA0214, AA0139, AA0210, AA0204, AA0205, AA0072) as "pointless"/unsolvable, and two AppSource rules (AS0084, AS0081) are deferred — don't reintroduce Fix suggestions for those unless AppSource submission is actually in scope.

## Architecture

### Contract lifecycle

A "contract" is just a `Sales Header` / `Purchase Header` with `"Document Type" = "Red Regenerator"` (enum value added by `SalesDocumentType.EnumExt.al` / `PurchaseDocumentType.EnumExt.al`) and a set of `Red Reg *` fields added by table extensions. Contract status (`Red Reg Contract Status` enum, `Setup/ContractStatus.Enum.al`) flows:

```
Concept → Accepted → Active → (Expired | Closed | Canceled)
```
(There's also `AutoGenerated` for contracts spawned from a posted document.) The flow is documented as a comment at the bottom of `ContractStatus.Enum.al` — read it before touching lifecycle logic.

Per-record lifecycle actions (accept/activate/close/cancel/renew/regenerate/archive, plus their `RedRegShowX` visibility predicates) live as `RedReg*` procedures directly on `SalesHeader.TableExt.al` / `PurchaseHeader.TableExt.al` (see `Area Sales/SalesHeader.TableExt.al`, `Area Purchase/PurchaseHeader.TableExt.al`). Cross-document orchestration (creating the next Order/Invoice from a contract, checking a period hasn't already been billed, activating a contract when its source document ships) lives in `Regenerator/Regenerator.Codeunit.al` (codeunit 70645, `TableNo = "Sales Header"` but with overloads for both Sales and Purchase headers).

Two "Generator" codeunits (`Regenerator/SalesGenerator.Codeunit.al`, `Regenerator/PurchaseGenerator.Codeunit.al`) build a *new* contract from an existing sales/purchase document or from Item/G/L/Resource contract templates — distinct from the Regenerator, which turns an *existing* contract into its next billing document.

### Sales ↔ purchase contract linking

Purchase contracts can carry a `Red Reg Sales Contract No.` / `Red Reg Sales Contract Ln. No.` back-reference (see `PurchaseHeader.TableExt.al`, `PurchaseLine.TableExt.al`) so that a purchase-side regeneration can be tied to the sales contract that spawned it (drop-ship / back-to-back contract scenarios). When creating documents in `Regenerator.Codeunit.al`, this link is carried forward explicitly — don't drop it when touching `CreatePurchaseDocument`/`CreateSalesDocument`.

### Templates and setup

- `Setup/Setup.Table.al` (`Red Reg Setup`, singleton) holds no. series for generated sales/purchase docs, post-commit suppression flags, and archive-on-close/cancel/renew behavior (`Action on Close`/`Action on Cancel`/`Action on Renew` options: blank / Archive / Archive and delete).
- `Setup/ContractGroup.Table.al` (`Red Reg Contract Group`) determines whether regeneration produces an Order or an Invoice.
- `Regenerator/SalesContrTemplate.Table.al` / `PurchContrTemplate.Table.al` define reusable contract line templates (by G/L Account / Item / Resource).
- `Regenerator/SalesItemContract.Table.al` (`Red Reg Sales Item Contract`) maps an Item (or G/L Account/Resource) to a contract template so a contract line can be auto-added when that item appears on a regular sales order line — this is the "automatically add item contract to sales order line" feature; see `Area Sales/SalesOrderSubform.PageExt.al` / `SalesLine.TableExt.al` for the hook point.

### Archiving

Sales/Purchase contract archives are separate table extensions + pages under `Area Sales/Archive/` and `Area Purchase/Archive/` (`SalesHeaderArchive.TableExt.al`, `PurchHeaderArchive.TableExt.al`, etc.), following BC's native document-archive pattern. Archive reason is captured via `Setup/ArchiveReasonCode.Table.al`. Archiving is triggered both automatically (per the `Red Reg Setup` "Action on ..." options, including on renew) and manually from the contract pages.

### ID ranges and naming conventions

- Main app object IDs: 70600–70799. Test app: 70800–70849. Stay inside these ranges for new objects (`app.json` `idRanges`); `app-source.json` uses a legacy AppSource-only ID range (11311113–11311212) — don't copy IDs from there.
- All AL objects/fields/procedures added by this extension are prefixed `Red Reg` (captions/fields) or `RedReg` (procedure names) — follow this exactly for discoverability and to avoid clashing with base app or other PTEs; the `namespace Red.Regenerator;` / `Red.Regenerator.Test` directive is required at the top of every file.
- `internal`/`Access = Internal` is used deliberately on cross-object entry points (e.g. `Regenerator.Codeunit.al` is `Access = Internal`) — keep new lifecycle/orchestration procedures internal unless they're meant to be a public extensibility surface.

### AL MCP server

`Documentation/al-mcp-prerequisites.md` and `al-mcp-repo-setup.md` describe wiring up the `al-language` MCP server (`.mcp.json`, `.claude/settings.json` → `enabledMcpjsonServers`). Neither file exists in the repo yet — if the user asks for AL diagnostics/symbol search/build via the MCP server, follow those two docs to set it up rather than guessing at args or paths.
